Architecture Approaches

How should the system be structured?

A

Monolith API + Next.js Frontend (Recommended)

Single FastAPI backend handles everything: RSS polling, content extraction, EPUB generation, Kindle delivery. Next.js frontend for browsing and selection.

Pros

  • Simple deployment — one backend process
  • Shared state — no message queues needed
  • Familiar stack from content_evaluation
  • SQLite for feed/article storage

Cons

  • EPUB generation blocks the API if not async
  • All logic in one service
B

Background Worker + API + Frontend

FastAPI serves the UI API. A separate background worker (Celery/ARQ) handles RSS polling, content fetching, and EPUB generation asynchronously.

Pros

  • Non-blocking — heavy work runs in background
  • Scalable — can add more workers
  • Clean separation of concerns

Cons

  • More infrastructure (Redis/queue)
  • Overkill for a personal tool
  • More complex deployment
C

Monolith + Background Tasks (via FastAPI)

Same as A, but uses FastAPI's BackgroundTasks or asyncio tasks for EPUB generation and delivery. No external queue, but heavy work doesn't block the API.

Pros

  • Simple like A, non-blocking like B
  • No extra infrastructure
  • FastAPI BackgroundTasks is built-in

Cons

  • Tasks lost on restart (no persistence)
  • Limited observability into background work
